### Sugestões

1. **`app/scripts/rodar-android.js:19-20` — o exemplo de uso do cabeçalho contradiz o README no
   shell desta máquina.** O cabeçalho ensina `npm run android:cabo -- --sem-compilar --sem-metro`.
   No PowerShell o `--` some, o npm toma as duas opções como configuração própria e só avisa
   `Unknown cli config`. O script então roda **sem opção nenhuma**: compila com o Gradle e sobe o
   Metro, o contrário do que foi pedido.

   Reproduzi com `npm run lint -- --sem-compilar --porta-do-servidor 8770`, que virou
   `eslint . 8770`. Com `--porta-do-servidor` o script recusa o `8770` solto, então falha com
   segurança. Com `--sem-compilar`, `--sem-metro` e `--todas-as-arquiteturas` a perda é
   silenciosa.

   Proposta: trocar o exemplo por `node scripts/rodar-android.js --sem-compilar --sem-metro`, como
   o README já faz. Se quiser blindar, há um caminho: o npm exporta a opção engolida como variável
   de ambiente. Conferi que `npm exec --sem-compilar` expõe `npm_config_sem_compilar`. O script pode
   recusar quando achar `npm_config_sem_compilar`, `npm_config_sem_metro`,
   `npm_config_todas_as_arquiteturas` etc., com a frase "o PowerShell engoliu o `--`; use node
   scripts/rodar-android.js …".

2. **`app/scripts/rodar-android.js:303` com `:165-182` e `:433-434` — stderr do adb é lido como se
   fosse saída.** `rodar()` junta stdout e stderr, e `lerAparelhos` lê o resultado inteiro. O adb
   escreve no **stderr** linhas como "adb server version (40) doesn't match this client (41);
   killing...". Testei a função com essa saída e ela devolveu
   `[{RQ8N209ND8Z, device}, {adb, server}]`. O `escolherAparelho` então recusou com "há 2 aparelhos
   conectados; escolha um com --aparelho: RQ8N209ND8Z (device), adb (server)". O mesmo vale para o
   `getprop` da ABI: um aviso no stderr suja a ABI e a compilação é recusada com uma mensagem
   enganosa.

   Falha com segurança (recusa, não instala no aparelho errado) e some na segunda execução. Mesmo
   assim, a mensagem confunde. `server/scripts/adb-reverse.mjs:101-110` e `:120-124` já resolvem
   isso: separam stdout de stderr e só leem as linhas depois do cabeçalho. Faltou um teste com essa
   saída em `rodarAndroid.test.ts`.

3. **`app/scripts/rodar-android.js:307-331` contra `server/scripts/adb-reverse.mjs:48-80` — duas
   regras diferentes para achar o adb no mesmo repositório.** O script do servidor aceita
   `CONTROLE_ADB` e procura no PATH; este não aceita nenhum dos dois, e lê o `local.properties` antes
   de tudo. Se um dia os dois scripts acharem adb de versões diferentes, cada um derruba o servidor
   adb do outro, e é exatamente aí que a sugestão 2 aparece. Hoje não acontece: não há adb no PATH
   desta máquina, e os dois chegam a `D:\Android\Sdk`.

   Proposta: aceitar ao menos `CONTROLE_ADB`, ou registrar no cabeçalho por que a ordem é outra. O
   argumento do `local.properties` (o mesmo SDK do Gradle) é bom e vale estar escrito nos dois.

4. **`app/scripts/rodar-android.js:532-533` — reaproveita qualquer Metro na 8081, mesmo de outro
   projeto.** O `/status` responde `packager-status:running` para qualquer Metro. O CLI do RN confere
   também o cabeçalho `X-React-Native-Project-Root`
   (`node_modules/@react-native-community/cli-tools/build/isPackagerRunning.js:33`) e não reaproveita
   o Metro de outro projeto. Aqui o app abriria com o bundle errado. Numa máquina com um projeto RN
   só, não acontece.

5. **`app/scripts/rodar-android.js:505-523` — o `adb reverse` fica para trás quando a porta do PC é
   outra.** Com `--porta-do-servidor 8770`, depois que o script sai, a 8765 do celular continua
   apontando para a 8770. Um `npm run dev` normal na 8765, em seguida, deixa o app "tentando
   conectar" sem motivo aparente até alguém refazer o encaminhamento. O próprio desenvolvedor
   precisou remover os dois à mão. Proposta: quando `portaDoServidor !== 8765`, imprimir no fim o
   comando que desfaz (`adb reverse --remove tcp:8765`) ou desfazer na saída. Com a porta padrão,
   manter o encaminhamento, como hoje.

6. **`app/README.md:51` — o "caminho oficial" em outra máquina não chega ao servidor.** "JDK 17 +
   `npm run android`" compila e abre o app, mas o próprio README diz (`:50`) que o run-android não
   encaminha a 8765. Vale completar com `cd server && npm run adb:reverse`, que já existe. A
   alternativa é dizer que o `android:cabo` também serve em outra máquina com `--java-home`.

## O que ficou bom

A entrega foi transparente nos dois lugares em que seria fácil não ser. Quando o AMSI barrou o
`.ps1`, a reação foi trocar de linguagem para o padrão do projeto, sem tentar passar pela heurística,
e o evento foi registrado. O critério que não deu para rodar ficou desmarcado e justificado. As peças
puras ficaram separadas dos efeitos (`require.main === module`), o que permitiu 22 testes sem
aparelho. O caminho de erro mata o Metro em toda saída, e isso se confirmou na prática. O caso da tela
bloqueada é o tipo de conferência barata que poupa meia hora de suspeita no build. Repetir isso.
