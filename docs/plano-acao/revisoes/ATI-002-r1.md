### Ctrl+C de verdade — o que o relatório não conseguiu testar, eu testei

O relatório declara (com honestidade) que no Windows não dá para entregar um Ctrl+C de
console a um processo filho pelo shell, e por isso usou `process.emit('SIGINT')` **dentro**
do próprio processo. Isso não exercita o caminho do `npm run dev`.

Dá para fazer o Ctrl+C real: `AttachConsole(pid)` + `SetConsoleCtrlHandler(NULL, TRUE)` +
`GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)` via P/Invoke no PowerShell. Fiz isso, com uma
sonda que registra uma tarefa de encerramento que grava um arquivo com `writeFileSync`
(síncrono — se a tarefa rodar, o arquivo existe).

| Caminho | Ctrl+C **real** | Tarefas de encerramento rodaram? |
|---|---|---|
| `node dist/principal.js` (= `npm start`) | processo sai sozinho em **8 ms** | **Sim** — `encerrando motivo=SIGINT tarefas=1` + `encerrado` |
| `npm run dev` (`tsx watch`) | árvore sai em **16 ms**, sem processo órfão | **Não** — nenhuma linha de encerramento, arquivo da sonda nunca criado |
| `node --watch dist/principal.js` | sai sozinho | **Parcial** — `encerrando` sai, `encerrado` não |
| `node --watch --import tsx src/principal.ts` | sai sozinho | **Parcial** — `encerrando tarefas=2` sai, arquivo da sonda nunca criado |

Também confirmei, por `SIGINT` emitido no processo (o mesmo teste do relatório), que
`getActiveResourcesInfo()` vai de `["Timeout"]` para vazio e o processo sai com **código 0**
sem `process.exit()`. O módulo `encerramento.ts` está certo; quem quebra o contrato é o
runner do script `dev`.

## Apontamentos

### Bloqueantes

1. **`server/package.json:9`** — `"dev": "tsx watch src/principal.ts"`, combinado com o
   critério de aceite marcado `[x]` em `docs/plano-acao/entregas/ATI-002-v1.md:68`.

   **O que está errado:** o critério é *"`npm run dev` sobe o processo e encerra limpo com
   Ctrl+C (sem handle pendente)"*. Com Ctrl+C **real**, `npm run dev` sobe (isso está certo)
   e a árvore morre rápido e sem órfão — mas **nenhuma tarefa de encerramento roda**: o
   `tsx watch` termina o processo neto sem que ele veja o SIGINT. Minha sonda registrou uma
   tarefa que faz `writeFileSync` e o arquivo nunca foi criado; nem a linha `encerrando` nem
   a `encerrado` apareceram no stderr. A evidência apresentada no relatório
   (linhas 145–149: *"fonte via tsx (mesmo caminho do npm run dev)"*) foi produzida por
   `process.emit('SIGINT')` dentro do processo, o que pula o supervisor do `tsx` —
   justamente a peça que falha. O critério está marcado com evidência de outro caminho.

   **Por que importa:** `encerramento.ts` é o caminho garantido de soltura da regra 5 do
   `CLAUDE.md` ("estado preso é o pior bug"). Hoje custa zero, porque a única tarefa é um
   timer ocioso que morre junto com o processo. A partir da **ATI-007** a tarefa de
   encerramento é o que solta botão de mouse e tecla pressionada no Windows. Se ela não roda
   no `npm run dev` — o modo usado o dia inteiro durante o desenvolvimento — cada Ctrl+C de
   desenvolvimento deixa tecla presa no sistema operacional. Congelar o runner agora, com o
   critério verde, garante que ninguém volta a olhar isso.

   **O que se espera:** uma das duas.
   (a) Um script `dev` em que o Ctrl+C real chega ao processo do servidor e as tarefas
   registradas terminam, comprovado com medição reproduzível (linhas `encerrando`/`encerrado`
   ou arquivo-marca, como fiz aqui) — vale testar as variantes de `node --watch`, mas nas
   duas que medi as tarefas também não terminaram, então não é um "troca o script e pronto".
   (b) O critério **desmarcado**, a limitação escrita em `server/README.md` (hoje, na linha
   31, ele afirma o contrário: *"o servidor solta o que registrou e o processo sai sozinho"*)
   e no cabeçalho de `encerramento.ts`, mais uma ATI nova para resolver isso **antes** da
   ATI-007, já que é ela que passa a ter estado para soltar.
   Em qualquer dos casos, corrigir no relatório a afirmação de que `process.emit('SIGINT')`
   é "o mesmo caminho do `npm run dev`".

### Importantes

2. **`server/package.json:14`** — `"lint": "npm run typecheck"`.

   **O que está errado:** a ATI (`docs/plano-acao/atividade/ATI-002.md:24`) pede os scripts
   `typecheck` **e** `lint` como itens distintos. Como está, `npm run lint` não roda linter
   nenhum: roda o mesmo `tsc` duas vezes. A decisão nº 3 do relatório
   (`ATI-002-v1.md:48-50`) se apoia em *"a diretriz autorizava explicitamente o apelido"* —
   procurei por `lint` em `CLAUDE.md`, `.claude/skills/desenvolvedor/SKILL.md`,
   `.claude/skills/revisor/SKILL.md` e em todo `docs/**`, e as únicas ocorrências são a
   própria linha da ATI, o `cd app && npm run lint && npm test` da skill do revisor e o
   relatório. **Não existe essa autorização.**

   **Por que importa:** script que se chama `lint` e não lint-a é verde falso. Na hora em que
   um CI, o orquestrador ou o próprio revisor rodar `npm run typecheck && npm run lint`, vai
   acreditar que há um portão de qualidade que não existe — e os dois comandos são
   literalmente o mesmo processo. O argumento de peso do relatório (evitar dependências) não
   se aplica: a ATI restringe dependências **de produção**, e linter é `devDependency`.

   **O que se espera:** ou um linter de verdade nesta ATI (ESLint flat config +
   `typescript-eslint`, tudo em `devDependencies`, o que não fere nenhum critério de aceite),
   ou o script `lint` **fora** do `package.json` com o desvio registrado na própria ATI, para
   ficar visível que o item não foi entregue. Entregar um apelido que reporta sucesso não é
   nenhuma das duas.

3. **`server/src/log.ts`** — módulo inteiro sem um único teste; em especial o filtro de
   nível em `log.ts:108-111` (`escrever`) e `log.ts:120` (`habilitado`).

   **O que está errado:** `config.ts` e `encerramento.ts` têm 17 casos entre os dois; `log.ts`
   tem zero. Nada assere que um `registrador.depuracao(...)` num registrador de nível `info`
   **não escreve nada**, que o escopo aparece entre colchetes, que `chave=valor` formata
   `Error` e objeto sem explodir, ou que `comEscopo()` preserva o destino.

   **Por que importa:** esse early-return é o mecanismo que torna aplicável a regra 2 do
   `CLAUDE.md` e a própria linha de escopo da ATI (*"nada de log por pacote no caminho
   quente"*). A partir da ATI-006 o código de 100 Hz vai depender de `habilitado()` e do
   descarte por severidade para não pagar nada; uma regressão silenciosa na comparação
   devolve escrita em stderr para dentro do caminho quente, que é exatamente o que esta ATI
   se propõe a impedir. É também o módulo do qual todos os próximos dependem.

   **O que se espera:** `server/src/log.teste.ts` cobrindo no mínimo: filtro de nível nos dois
   sentidos (o que sai e o que **não** sai), `habilitado()`, escopo na linha e formatação de
   `chave=valor` para string com espaço, número, `null`, `undefined`, `Error` e objeto. O
   custo é baixo de propósito: `criarRegistrador` já recebe `destino` injetável
   (`log.ts:104`) exatamente para isso, e `encerramento.teste.ts:12-14` já usa esse recurso.

### Sugestões

4. **`server/src/encerramento.ts:106`** — o comentário diz que o servidor WebSocket entra na
   **ATI-004**. Pelo `planejamento.md:36-37`, ATI-004 é o codec do protocolo e ATI-005 é o
   transporte WebSocket; o próprio `server/README.md:7-8` e a decisão nº 6 do relatório dizem
   ATI-005. Como é justamente o comentário que diz *quando apagar a âncora*, apontar para a
   ATI certa evita que o andaime fique esquecido.

5. **`server/src/config.ts:247`** — a checagem `porta === portaDescoberta` só roda quando
   `problemas.length === 0`, o que contraria a promessa do próprio módulo
   (`config.ts:11`: *"lista completa de problemas"*). Com
   `CONTROLE_TAXA_HZ=rapido CONTROLE_PORTA_DESCOBERTA=8765` o usuário corrige a taxa e só na
   execução seguinte descobre o choque de portas. A cautela é legítima (um valor que caiu no
   padrão pode colidir por acidente), mas dá para ter as duas coisas: comparar quando os dois
   valores passaram pela validação sem problema próprio.

6. **`server/src/principal.ts:56`** — `principal()` roda no import, então o ponto de entrada
   nunca poderá ser importado por um teste e qualquer import acidental sobe o servidor. Uma
   guarda (`process.argv[1]` resolvido contra `fileURLToPath(import.meta.url)`) mantém
   `npm start` e `npm run dev` idênticos e deixa o módulo testável quando houver o que testar.

## O que ficou bom

O `config.ts` está acima da média: três camadas com precedência explícita, erro que junta
**todos** os problemas de uma vez com o nome da variável que causou cada um, chave
desconhecida recusada em vez de engolida, e a distinção certa entre "arquivo padrão ausente"
e "arquivo pedido de propósito e ausente". A separação `tsconfig.json` (checa tudo, inclusive
teste) × `tsconfig.build.json` (não leva teste para `dist/`) é limpa e eu confirmei que
funciona. Os oito READMEs de pasta dizem o que vai morar ali e em qual ATI — conferi as
referências uma a uma contra o `planejamento.md` e todas batem (menos a do item 4). E o
relatório de entrega declara as limitações em vez de escondê-las, inclusive a do Ctrl+C —
foi essa honestidade que me fez ir procurar o teste que faltava, e é o que deve se repetir.

Detalhe menor, sem apontamento: a tabela de arquivos do relatório diz "12 casos" em
`config.teste.ts` e "5" em `encerramento.teste.ts`; são 11 e 6. O total, 17, está certo.
