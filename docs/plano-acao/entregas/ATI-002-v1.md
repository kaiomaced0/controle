# Entrega ATI-002 — rodada 1

## O que foi feito

Esqueleto do servidor do PC em `server/`: pacote ESM Node >= 22 sem nenhuma dependência de
produção, TypeScript estrito (`strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`,
ES2023 + NodeNext), `tsx` como runner de desenvolvimento e build com `tsc`.
`src/config.ts` é a fonte única dos padrões (host, porta, portaDescoberta, taxaHz, nivelLog),
com três camadas de precedência — padrão → arquivo JSON opcional → variáveis `CONTROLE_` —
validação de faixa e erro que lista todos os problemas de uma vez. `src/log.ts` é um logger
próprio de quatro níveis escrevendo em stderr, com o aviso de que o caminho quente não loga
por pacote. `src/encerramento.ts` garante a saída limpa no Ctrl+C/SIGTERM sem handle pendente.
As seis pastas da arquitetura (mais `perfis/`) nasceram com um README curto cada.
Testes com `node:test`: 17 casos cobrindo carga de configuração e encerramento.

## Decisões tomadas

1. **Precedência padrão → arquivo → ambiente.** A ATI pede configuração "por arquivo +
   variáveis de ambiente" e a diretriz pede sobreposição por `CONTROLE_`; as duas convivem
   com o ambiente vencendo — é o que permite trocar a porta numa execução só sem editar
   arquivo. Arquivo padrão ausente não é erro; arquivo pedido de propósito
   (`CONTROLE_ARQUIVO_CONFIG`) e ausente é erro, para não engolir caminho digitado errado.
2. **Valor inválido derruba, não satura.** No `config` do protocolo (PROTOCOLO.md 3.4) o
   servidor satura valores fora da faixa, porque ali quem manda é o usuário mexendo no
   celular em tempo real. Na configuração de partida o oposto é melhor: `CONTROLE_PORTA=70000`
   é erro de digitação, e subir em outra porta em silêncio custaria uma hora de depuração.
   Todos os problemas saem de uma vez, não um por execução.
3. **`lint` é apelido de `typecheck`.** Não instalei ESLint: seriam ~8 pacotes a mais, um
   flat config novo e regras a decidir — trabalho que não é desta ATI (a diretriz autorizava
   explicitamente o apelido). O script existe e passa; trocar por ESLint de verdade é ATI nova.
4. **Chave desconhecida no arquivo é erro.** `{"portta": 8765}` seria silenciosamente ignorado
   e o servidor subiria na porta errada. A mensagem lista as chaves aceitas.
5. **`porta` e `portaDescoberta` não podem ser iguais.** Deixaria a descoberta UDP da fase 3
   sem lugar; melhor recusar agora do que descobrir na ATI-013.
6. **Âncora do event loop.** Sem transporte, nada segura o processo vivo e ele sairia antes de
   qualquer Ctrl+C. `ancorarEventLoop()` é um timer ocioso registrado como tarefa de
   encerramento; sai quando o WebSocket entrar (ATI-005) e passar a ser a âncora natural.
7. **Sem `process.exit()` no caminho normal.** O processo sai porque não sobrou handle. Se
   sobrar, ele trava e o bug aparece — mascarar com `exit()` esconderia exatamente o defeito
   que o critério de aceite quer pegar. Só há saída forçada no estouro do limite de 5 s.
8. **Teste ao lado do código, sufixo `.teste.ts`** (PT-BR, como manda o CLAUDE.md), rodado por
   `node --import tsx --test "src/**/*.teste.ts"`. O `tsconfig.build.json` mantém `dist/` limpo.
9. **Log em stderr.** stdout fica reservado para a telemetria da CLI (ATI-006), então dá para
   acompanhar as duas coisas ao mesmo tempo sem uma atrapalhar a outra.

## Critérios de aceite

- [x] **`npm run dev` sobe o processo e encerra limpo com Ctrl+C (sem handle pendente).**
  `npm run dev` sobe (saída colada abaixo). O encerramento foi verificado nos dois caminhos
  (fonte via `tsx` e `dist/`) com um roteiro que emite SIGINT — o mesmo sinal do Ctrl+C — e
  observa a saída: o processo executou as tarefas e **saiu sozinho com código 0**, sem
  `process.exit()`. Ressalva honesta: no Windows não dá para entregar um Ctrl+C de console a
  um processo filho a partir do shell (`process.kill(pid,'SIGINT')` mata sem entregar o
  sinal), então o disparo foi por `process.emit('SIGINT')` dentro do próprio processo, que
  aciona o mesmo ouvinte. O Ctrl+C digitado num terminal interativo não foi testado por mim.
- [x] **`npm run typecheck` passa com `strict: true` e sem `any` implícito.**
  Passa sem nenhuma saída. O `tsconfig.json` liga `strict`, `noUncheckedIndexedAccess`,
  `noImplicitOverride`, `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`,
  `exactOptionalPropertyTypes` e `verbatimModuleSyntax`, e cobre também os testes.
- [x] **`npm test` executa e passa.** 17 testes, 3 suites, 0 falhas.
- [x] **Configuração documentada no README do `server/` com os padrões e como sobrescrever.**
  Tabela com campo, padrão, variável e faixa, mais exemplos de linha de comando, a regra de
  precedência e a mensagem de erro real.
- [x] **Dependências de produção limitadas ao necessário; nada de framework web.**
  `npm ls --omit=dev --depth=0` → `(empty)`. As três devDependencies são `typescript`, `tsx`
  e `@types/node`.

## Achados fora do escopo

1. **`.gitignore` não cobre `server/controle.config.json`.** O arquivo de configuração local
   é ajuste de máquina e não deveria ser versionado. Não mexi no `.gitignore` da raiz porque
   está fora do escopo desta ATI e outro agente pode estar trabalhando em paralelo.
   *Sugestão de ATI:* acrescentar `server/controle.config.json` ao `.gitignore` (uma linha).
2. **ESLint não existe em `server/` nem regra comum entre `app/` e `server/`.** O `app/` usa
   `@react-native/eslint-config` + prettier; o servidor não tem linter. *Sugestão de ATI:*
   escolher e configurar o linter do servidor (ESLint flat config + `typescript-eslint`), com
   `npm run lint` de verdade nos dois pacotes.
3. **README da raiz diz "O servidor do PC ainda é um scaffold — será implementado na ATI-002"
   e a tabela de stack cita WebSocket (`ws`).** A frase fica desatualizada com esta entrega, e
   a escolha da biblioteca de WebSocket é decisão da ATI-005. *Sugestão de ATI:* passada de
   atualização no README da raiz e no `CLAUDE.md` (seção "Estado atual") ao fim do sprint 1.
4. **Nome do pacote do app é `controle-app` e o do servidor ficou `controle-server`** — meio
   inglês, meio português, mas seguindo o nome da pasta (`server/`), que é o que já existia.
   Renomear pasta e pacote seria mudança grande para ganho estético. *Sugestão de ATI:* só se
   o Kaio quiser padronizar tudo em PT-BR de uma vez.

## Riscos e limitações

- **Ctrl+C real não foi testado num console interativo** (esta sessão não é interativa e o
  Windows não deixa entregar SIGINT a um filho pelo shell). O que foi provado: o ouvinte de
  SIGINT roda as tarefas e o processo sai sozinho, com código 0, sem `exit()` forçado.
- **`tsx watch` não foi exercitado com uma alteração de arquivo**, só a subida inicial. Se a
  recarga tiver algum problema, ele aparecerá na primeira edição em desenvolvimento.
- **A âncora do event loop é andaime.** Se a ATI-005 esquecer de removê-la depois que o
  servidor WebSocket segurar o processo, sobra um timer de 60 s inofensivo, mas inútil.
- **Nível de log não é ajustável em tempo de execução** (só na partida). Se a telemetria da
  ATI-006 precisar disso, é fácil acrescentar — o registrador já é criado num ponto só.
- **`process.getActiveResourcesInfo()`** é usada no teste da âncora; é API estável do Node,
  mas é introspecção do runtime — se algum dia mudar, o teste é o que quebra, não o servidor.
