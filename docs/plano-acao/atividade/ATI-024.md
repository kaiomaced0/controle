# ATI-024 — Desbloquear o build Android nesta máquina

## Situação
**Nenhum build Android roda nesta máquina.** Qualquer `gradlew` falha antes de compilar:

```
FAILURE: Build failed with an exception.
* What went wrong:
java.io.IOException: Unable to establish loopback connection
```

## Diagnóstico feito (2026-08-20)

A mensagem vem do **JDK**, não do Gradle. Foi isolada assim:

| Teste | Resultado |
|---|---|
| Socket de loopback em Node | **funciona** |
| Socket de loopback em Java (bloqueante) | **funciona** |
| `Pipe.open()` em Java | funciona |
| `Selector.open()` em Java (NIO) | **falha** — mesma mensagem |
| Mesmo teste com o JDK do Android Studio (JBR 21.0.6) | **falha igual** |
| Mesmo teste fora do sandbox do shell | **falha igual** |

`Selector.open()` no Windows precisa criar um par de sockets de wakeup e **aceitar uma
conexão de entrada em loopback**. É exatamente esse passo que está sendo barrado — e o
daemon do Gradle depende dele, então o build morre antes de compilar qualquer coisa.

Ambiente encontrado:

- Rede: `sefaz.to.gov.br` (DomainAuthenticated)
- **Kaspersky Endpoint Security 14.0** com Agente de Rede do Kaspersky Security Center
  (gerenciado centralmente pela organização)
- Duas regras do firewall do Windows: `Java(TM) Platform SE binary` — Inbound / **Block** /
  perfil Public, apontando para `C:\Program Files\Java\jdk-21\bin\java.exe`

O bloqueio não é apenas dessas duas regras: o JBR do Android Studio, que tem outro caminho e
nenhuma regra própria, falha do mesmo jeito. O comportamento aponta para o componente de
firewall/prevenção de intrusão do Kaspersky, que é política da organização.

## O que fazer (decisão do Kaio, não do agente)

Nenhuma tentativa de contornar controle de segurança corporativo foi feita, nem deve ser.
Caminhos legítimos, do mais simples ao mais burocrático:

1. **Exceção no Kaspersky** para `java.exe` (JDK e JBR) e para o processo do Gradle,
   solicitada a quem administra o Kaspersky Security Center da SEFAZ-TO.
2. **Remover as duas regras Inbound/Block** do firewall do Windows para o `java.exe` do JDK
   (precisa de administrador) — ajuda, mas sozinha provavelmente não resolve, pelo teste do JBR:
   ```powershell
   Get-NetFirewallRule -DisplayName "Java(TM) Platform SE binary" |
     Where-Object { $_.Action -eq "Block" -and $_.Direction -eq "Inbound" } | Remove-NetFirewallRule
   ```
3. **Compilar em outra máquina** (pessoal, sem o agente corporativo) e instalar o APK aqui —
   `adb install` não depende do Gradle.

## Impacto enquanto estiver bloqueado

- Todo o **lado PC** funciona e é verificável: servidor, protocolo, transporte, simulador e
  telemetria (Node não usa o `Selector` do Java).
- O **lado app** fica verificável apenas por TypeScript e Jest. O módulo nativo Kotlin da
  ATI-003 **nunca foi compilado** — pode ter erro de compilação ainda desconhecido.
- O teste ponta a ponta celular ⇄ PC (e também no emulador) **depende desta ATI**.

## Critérios de aceite
- [x] `cd app/android && ./gradlew assembleDebug` conclui e gera o APK de depuração — com JDK 18 e as
  duas chaves (seção "Resolvido em 2026-10-13"); repetido em 2026-10-14 pelo script, só com a ABI do
  aparelho: `BUILD SUCCESSFUL in 1m 30s`, APK de 36,9 MB.
- [x] `npx react-native run-android` instala e abre o app no aparelho — com `JAVA_HOME` no JDK 18 e

  `npm run android:cabo`.
- [x] Registrar aqui o que resolveu, para não se perder da próxima vez — seções abaixo.

## Resolvido em 2026-10-13 — sem mexer em segurança nenhuma

**O bloqueio é por executável Java, não do Java em geral.** Testado o `Selector.open()` em cada
JDK instalado:

| JDK | Resultado |
|---|---|
| 1.8.0_211 | OK |
| 17.0.2 | **falha** |
| **18.0.2** | **OK** |
| 21.0.3 | **falha** |
| JBR do Android Studio (21) | **falha** |

As regras do firewall do Windows só existem para o JDK 21 — o 17 falha sem regra nenhuma —, então
o filtro não é o firewall do Windows; o mais provável é o controle de aplicações do Kaspersky,
decidindo por executável.

Três obstáculos, três consertos:

1. **Daemon do Gradle no JDK 18** (`JAVA_HOME`), que passa no bloqueio.
2. **`local.properties` mal escapado** — erro meu da ATI-001: `D\:\Android\Sdk` em arquivo
   `.properties` vira `D:AndroidSdk`, porque `\A` e `\S` são escapes. Agora `sdk.dir=D:/Android/Sdk`.
3. **O React Native força toolchain Java 17** (`JdkConfiguratorUtils.kt`), o Gradle escolhe o
   `jdk-17.0.2` e abre um *Worker Daemon* nele — que é barrado. A chave oficial
   `react.internal.disableJavaVersionAlignment` desliga a exigência, e o javac roda dentro do
   próprio daemon (JDK 18). Passada pela **linha de comando**, para não mudar o projeto para quem
   tem máquina sem bloqueio.

O comando que funciona (Git Bash):

```bash
cd app/android
export JAVA_HOME="C:/Program Files/Java/jdk-18.0.2"; export PATH="/c/Program Files/Java/jdk-18.0.2/bin:$PATH"
./gradlew assembleDebug -Preact.internal.disableJavaVersionAlignment=true -Pkotlin.jvm.target.validation.mode=warning
```

Resultado: `BUILD SUCCESSFUL in 3m 55s`, `app-debug.apk` de 117 MB. **O Kotlin da ATI-003
compilou sem erro** na primeira vez que viu um compilador.

Falta para fechar: instalar e rodar no aparelho (`run-android` / `adb install` + Metro).

⚠️ Bytecode compilado com JDK 18 mirando a mesma versão que o RN pede funciona, mas é contorno de
máquina: em máquina sem bloqueio, o caminho normal (JDK 17) continua sendo o oficial.

## Rodar no aparelho — 2026-10-14 (Galaxy S20+, SM-G985F, Android 13)

**Um comando só**, de dentro de `app/` (PowerShell ou qualquer terminal):

```powershell
npm run android:cabo
```

O [`app/scripts/rodar-android.js`](../../../app/scripts/rodar-android.js) monta o JDK 18 só para o
Gradle, compila **só a ABI do aparelho** conectado (como o `--active-arch-only` do run-android:
36,9 MB em vez de 117 MB), instala com `adb install -r`, faz `adb reverse` da 8081 (Metro) e da 8765
(servidor), sobe o Metro no mesmo terminal (Ctrl+C encerra), abre `com.nortedata.controle/.MainActivity`
e avisa se a tela estiver bloqueada ou se o processo do app morrer logo depois de abrir. Opções e
problemas comuns: [`app/README.md`](../../../app/README.md).

O `run-android` também funciona, desde que o JDK e as chaves venham de fora:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-18.0.2'; $env:Path = "$env:JAVA_HOME\bin;$env:Path"
npx react-native run-android --active-arch-only --extra-params "-Preact.internal.disableJavaVersionAlignment=true -Pkotlin.jvm.target.validation.mode=warning"
```

Ele não encaminha a porta 8765 do servidor — por isso o caminho recomendado é o script.

O que apareceu no caminho, para não se perder:

1. **O script nasceu `.ps1` e o antivírus barrou.** Ao rodar no Windows PowerShell 5.1, o Kaspersky
   (via AMSI) bloqueou o arquivo como "conteúdo mal-intencionado" antes de executar uma linha.
   Nenhuma tentativa de contornar foi feita: o `.ps1` foi apagado e a orquestração foi para Node,
   que é o padrão de script de bancada do projeto (`server/scripts/adb-reverse.mjs`). O evento pode
   ter ficado registrado no console do Kaspersky da organização.
2. **No PowerShell, `npm run x -- --opção` perde o `--`** (o próprio PowerShell o consome). Opção vai
   com `node scripts/rodar-android.js --opção`.
3. **`gradlew.bat` sem `.\` falha quando `NoDefaultCurrentDirectoryInExePath` está no ambiente**
   (terminal de ferramenta, como o do agente): o cmd deixa de procurar na pasta atual. O script usa
   `.\gradlew.bat`; o `run-android` não tem esse ajuste, e num terminal assim falha com
   "'gradlew.bat' não é reconhecido".
4. **Tela bloqueada:** o `am start` abre a activity por trás do bloqueio; o app roda (o logcat mostra
   `Running "ControleApp"`), mas ninguém vê — e, no teste, a sessão com o servidor só abriu depois
   do desbloqueio.

**Prova, 2026-10-14 12:54 (horário do aparelho):** com a tela desbloqueada, o app em primeiro plano
mostrou "Conectado · sessão s-2", a aba Medição com o giroscópio LSM6DSO a 100,6 Hz, e o servidor
registrou `sessão aberta ... aparelho="samsung SM-G985F" ... transporte=usb` (na sessão anterior,
`rttP50=6`). Logcat sem `AndroidRuntime:E` e buffer de crash vazio; o `ControleTransporte` registrou
`TCP_NODELAY ligado nos WebSockets do app`. **O Kotlin da ATI-003 rodou pela primeira vez sem
precisar de conserto.**
