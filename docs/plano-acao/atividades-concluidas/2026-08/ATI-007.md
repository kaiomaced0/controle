# ATI-007 — Backend de entrada do Windows (SendInput via FFI)

## Objetivo
Fazer o servidor mexer o mouse de verdade no Windows: movimento relativo, três botões,
scroll e posicionamento absoluto.

## Escopo
- Interface `BackendDeEntrada` em `server/src/saida/` (contrato em ARQUITETURA.md, seção 2.3).
- Implementação Windows com `koffi` chamando `SendInput` da `user32.dll`:
  - `MOUSEEVENTF_MOVE` para movimento **relativo** (é o que o gyro aim exige)
  - `SetCursorPos` para o comando centralizar
  - botões esquerdo, direito e meio (down e up separados, nunca clique atômico)
  - `MOUSEEVENTF_WHEEL` e `MOUSEEVENTF_HWHEEL` com `WHEEL_DELTA` = 120
  - teclas por **scancode** (`KEYEVENTF_SCANCODE`), já preparando os perfis de teclado
- Structs `INPUT`, `MOUSEINPUT`, `KEYBDINPUT` declaradas com alinhamento correto em 64 bits;
  struct reaproveitada entre chamadas (sem alocar por evento).
- Consulta da resolução da tela (`GetSystemMetrics`) para o centro usado no centralizar.
- Modo de teste manual: `npm run dev -- --teste-mouse` faz um quadrado com o cursor e clica.

## Fora do escopo
Gamepad virtual (sprint 5) e qualquer lógica de sensor.

## Critérios de aceite
- [ ] O cursor se move, clica com os três botões e rola a página em aplicativos comuns.
- [ ] `SendInput` retorna 1 por evento; retorno diferente é registrado como erro.
- [ ] Botão pressionado permanece pressionado (arrastar funciona); soltar sempre acontece,
      inclusive se a conexão cair no meio (proteção contra botão preso).
- [ ] Nenhuma alocação por evento no caminho quente.
- [ ] Limitação conhecida documentada no README do servidor: títulos com anti-cheat rigoroso
      podem ignorar entrada injetada — para esses, o caminho é o gamepad virtual.

## Notas
`robotjs` e `nut.js` foram descartados (ADR-5): exigiriam toolchain de compilação ou
dependência instável. `koffi` distribui binário pré-compilado e nos dá controle byte a byte
das structs.
